# Архитектура

## Слои и зачем они разделены

```
arix/
├── config.py          настройки деплоя (всё остальное — в tenant_config)
├── channels/          адаптеры каналов: только парсинг вебхука и отправка
├── domain/            контакты, диалоги, история, доставка, передача человеку
├── core/              контекст тенанта, PII Guard, события, время, крипто
├── agent/             промпт, инструменты, два «мозга», guardrails, runtime
├── kb/                поиск по базе знаний
├── scheduler/         durable-задания и воркер
├── verticals/clinic/  слоты, запись, отзывы, отчёты, задания модуля
├── seed/              шаблоны YAML, провижининг, импорт Excel
├── api/               вебхуки, админ-API, панель, Mini App
├── bots/              команды администратора, владельца, врача
└── eval/              набор диалогов и приёмка
```

Границы выбраны так, чтобы **всё, кроме `verticals/`, было одинаковым** для
клиник и учебных центров. Рантайм общается с вертикалью через протокол
`VerticalAdapter` (`agent/runtime.py`), а планировщик — через реестр
обработчиков (`scheduler/registry.py`). Поэтому `edu-ai` — это тот же код ядра
плюс свой каталог вертикали.

## Инварианты, на которых держится система

### 1. Двойная запись невозможна на уровне БД

```sql
EXCLUDE USING gist (doctor_id WITH =, period WITH &&)
WHERE (status IN ('hold','booked','confirmed','arrived'))
```

Приложение не делает «прочитать — проверить — записать»: оно пробует вставку и
переводит `IntegrityError` в понятный ответ «это время только что заняли».
Под 50 одновременными диалогами проверка «сначала прочитать» давала бы гонку;
ограничение — нет. Это проверяется тестом
`test_concurrent_booking_of_one_slot_produces_exactly_one_visit`.

`period` включает буфер услуги, поэтому следующего пациента нельзя посадить
в технический перерыв врача.

### 2. Факты только из инструментов

Цены, услуги, врачи, слоты, адрес и политика приходят в ответ только через
вызовы инструментов. Три независимых слоя:

- **до модели** — `guardrails.precheck`: красные флаги, просьба человека,
  отказ от рассылок, запрос на удаление данных, торг, попытка выудить диагноз;
- **инструменты** — единственный источник фактов (`agent/tools_core.py`,
  `verticals/clinic/tools.py`);
- **после модели** — `guardrails.postcheck`: сообщение с суммой, диагнозом,
  гарантией или утечкой промпта **не отправляется**, вместо него создаётся
  передача администратору.

`list_services` отдельно сообщает `query_matched`: если запрос («пересадка
волос») не совпал ни с одной услугой, бот не цитирует первую строку прайса, а
передаёт вопрос человеку.

### 3. Идемпотентность на каждом входе и выходе

| Что | Ключ |
|---|---|
| входящее сообщение | `messages.external_id` уникален в тенанте |
| запись | `visits.idempotency_key` |
| задание планировщика | `scheduled_jobs.dedupe_key` уникален в тенанте |
| счётчик исходящих | `(tenant, channel, period)` |

Повторная доставка вебхука и повторный запуск бизнес-решения ничего не ломают.

### 4. Таймеры — записи в БД, а не `sleep`

`scheduled_jobs` — источник истины: задание видно поддержке, его можно
отменить бизнес-правилом, оно переживает перезапуск. Воркер берёт задания
через `FOR UPDATE SKIP LOCKED`-аренду, так что несколько воркеров делят
очередь без двойной доставки, а упавший воркер освобождает аренду по таймауту.

Исходящие задания проходят через тихие часы (`shift_out_of_quiet_hours`).
Единственное исключение задокументировано в коде: напоминание −2 ч для
утреннего визита переносится **вперёд**, на 08:00, а не назад на 09:00 —
иначе оно пришло бы после приёма.

### 5. Порядок сообщений детерминирован

`messages.seq` — монотонный `BIGSERIAL`. `created_at` по умолчанию равен
времени транзакции, поэтому входящее сообщение и ответ, записанные в одной
транзакции, имеют одинаковый timestamp; сортировка только по времени могла бы
слить два сообщения пациента в одно и сломать разбор ответа.

### 6. Изоляция тенантов — двумя способами

1. **RLS в Postgres.** Политика на `current_setting('arix.tenant_id')`,
   `FORCE ROW LEVEL SECURITY` на всех таблицах с `tenant_id`. GUC ставится на
   транзакцию в `db/session.tenant_session`. Роль приложения —
   **не суперпользователь** (`scripts/init-db.sql`), иначе Postgres обошёл бы
   политику.
2. **Фильтр в приложении.** Все запросы идут с `WHERE tenant_id = ...`.

Операции уровня ARIX (создание тенанта, кросс-тенантная панель) используют
`admin_session()`, который выставляет `arix.bypass_rls` и логируется в
`audit_log`.

## Конвейер одного сообщения

`agent/runtime.ConversationRuntime.handle`:

1. дедупликация по `external_id`;
2. контакт и диалог (идентичности каналов не создают двух пациентов);
3. голосовое → STT, в историю пишутся и аудио, и текст;
4. `precheck` — жёсткие маршруты: красный флаг → текст о срочности и
   передача с приоритетом `urgent`, минуя модель;
5. фото и документы → передача человеку, снимки не анализируются;
6. если диалог взял человек (или клиника ответила сама через Telegram
   Business) — бот молчит и пингует персонал;
7. маскирование ПД → промпт из конфига тенанта + состояние диалога;
8. «мозг» вызывает инструменты (не более `LLM_MAX_TOOL_ROUNDS` кругов);
9. `postcheck`, восстановление ПД, отправка, кнопки;
10. побочные эффекты: передача человеку, планирование напоминаний, лестница
    дожима, счётчик непонятых сообщений, события.

## Два «мозга», один набор инструментов

| | Claude | Детерминированный |
|---|---|---|
| когда | есть `ANTHROPIC_API_KEY` | нет ключа, или `LLM_FORCE_SCRIPTED=true` |
| инструменты | те же | те же |
| guardrails | те же | те же |
| зачем нужен второй | — | демо без сети, стабильный baseline в CI, работа при недоступности API |

Оба проходят `make eval` с одинаковой приёмкой. Это не заглушка: по сценариям
ТЗ §7 детерминированный движок закрывает цену, запись, перенос, отмену,
красные флаги, торг, FAQ и промпт-инъекции.

## Модель данных

Ядро: `tenants`, `tenant_config`, `channels`, `channel_routes`, `contacts`,
`contact_identities`, `conversations`, `messages`, `kb_items`,
`scheduled_jobs`, `sequences`, `handoffs`, `events`, `payments`, `staff`,
`outbound_counters`, `audit_log`, `daily_metrics`.

Клиника: `doctors`, `services`, `doctor_services`, `rooms`, `schedules`,
`schedule_exceptions`, `visits`, `waitlist`, `treatment_plans`, `reviews`.

Перечисления хранятся как строки с `CHECK`, а не как PG enum: добавить
значение не должно требовать блокировки таблицы живого тенанта.

## Атрибуция выручки

Каждая запись и каждая оплата помечаются источником: `bot`, `bot_night`,
`miniapp`, `followup`, `recall`, `reactivation`, `admin`. Отчёт «Доля» — сумма
оплат по атрибуции за месяц. Правило 14 дней между приглашением и записью
реализовано в задании `recall_invite`, которое ставит
`conversation.scratch.attribution = "recall"`.
